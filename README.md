# Cost accounting — новая версия

Учёт личных расходов. Postgres — источник истины, Google Spreadsheet — отчётная
поверхность и интерфейс редактирования справочников.

Система состоит из четырёх частей:

| Часть | Состояние | Ответственность |
|---|---|---|
| `api/` | готов | Владеет Postgres. Вся предметная логика и все деньги |
| `google_sheets_service/` | готов | Единственный, кто ходит в Google API. Разгребает очередь перерисовки листов, читает правки пользователя и отдаёт их в api |
| `telegram_bot/` | **этот шаг** | aiogram-фронтенд: разбирает ввод, зовёт api, печатает ответ на языке пользователя. Здесь же живёт разбор чека |
| `checks_service/` + `mini_app/` | готов | Единственная публичная часть системы: Mini App сканирует QR-код чека, сервис получает расшифровку и кладёт сырьё в api |

## Что сделано на этом шаге

**Мультиязычность.** Бот, уведомления и Mini App говорят на пяти языках: ru, en,
hi, es, fr. Язык выбирается на каждом `/start` — выбор с английской подписью,
приветствие уже на выбранном — и в настройках, кнопкой «Язык»: по четыре языка
на страницу. Хранится он в api, в `users.language`: язык — свойство человека, и
нужен он не только боту.

Весь текст пользователю живёт в боте, в каталогах
`telegram_bot/resources/locales/<код>/`, без исключений. Api отдаёт коды и данные
для подстановки: уведомления (`user_notifications.code` + `params`), отказы
импорта листа, 422 (`details.reason`). Числа и даты печатаются по правилам языка
через Babel. Модель предлагает новые типы товаров на языке пользователя, а
категорию по умолчанию бот и api узнают по флагу `is_default`, а не по названию:
в новых таблицах оно на языке пользователя.

Подробности: [docs/BOT_machine.md](docs/BOT_machine.md) §11,
[docs/API_machine.md](docs/API_machine.md) §9 (шаг 8) и
[docs/CHECKS_machine.md](docs/CHECKS_machine.md) §4.

Предыдущий шаг — разбор чека: `/check` превращает сырьё, накопленное Mini App, в
операции реестра ([docs/BOT_machine.md](docs/BOT_machine.md) §10).

## Ключевые архитектурные решения

**Api никогда не ходит в Google.** Изменение данных — одна короткая транзакция в
Postgres, которая заодно пишет строку в очередь `sheet_sync_tasks`. Отдельный
сервис разгребает очередь и перерисовывает листы, повторяя при сбоях. Поэтому
операция не может завершиться сообщением об ошибке после того, как деньги уже
списаны, — сценарий двойного списания при таймауте на стороне Google исчезает.

**Задача в очереди описывает не изменение, а устаревание.** Строка означает
«лист X таблицы Y больше не соответствует БД». Уникальный ключ
`(spreadsheet_id, target, period_id)` схлопывает десять быстрых правок в одну
задачу, а перерисовка идёт из текущего состояния БД целиком — поэтому повтор
безопасен, а порядок обработки не важен.

**Валюта — свойство самой операции.** Она называется в `/add` первым словом
либо берётся из формата чека, и хранится исходной: приведение к валюте листа
статистики зависит от курса на день операции и считается на лету. Записать в
реестр уже сконвертированное значило бы похоронить настоящую сумму покупки.

**Период — строка в таблице, а не подвижный указатель.** `periods` с уникальным
`(spreadsheet_id, start_date)` делает ролловер идемпотентным и позволяет догнать
любое число пропущенных месяцев. Границы полуинтервальные: `[start, end)`.

**Деньги — `NUMERIC(14,2)` и `Decimal`.** Ни одного `float`, ни одного
округления по пути от БД к листу.

**Принадлежность чужой таблице невыразима.** Составные внешние ключи
`(category_id, spreadsheet_id) → categories(id, spreadsheet_id)` не дают
сослаться на категорию из чужого документа — раньше это проверялось вручную в
каждом сервисе и местами было забыто.

**Текст пользователю живёт только в боте.** Api и сервисы отдают машинные коды и
данные, а фразу на языке пользователя собирает бот по своему каталогу. Иначе
уведомление, собранное api в момент события, было бы на одном языке для всех.

## Запуск

```bash
cp env/api.env.example env/api.env
cp env/postgres.env.example env/postgres.env
cp env/google_sheets_service.env.example env/google_sheets_service.env
cp env/telegram_bot.env.example env/telegram_bot.env
cp env/checks_service.env.example env/checks_service.env
cp env/grafana.env.example env/grafana.env
# заполнить пароли, положить ключ сервисного аккаунта в secrets/google_sa.json,
# указать TELEGRAM_BOT_TOKEN, PROVERKACHEKA_API_TOKEN и списки доступа —
# ALLOWED_TELEGRAM_IDS и ADMIN_TELEGRAM_IDS (одинаково боту и checks_service;
# доступ = объединение списков, дублировать админов в первом не нужно)
docker compose up -d --build
curl -s localhost:8010/health          # api
curl -s localhost:8011/health          # отчёт последнего прохода по очереди
curl -s localhost:8012/health          # бэкенд Mini App
```

Ни один порт наружу не публикуется: всё висит на `127.0.0.1`. Бот работает
через long polling и входящих соединений не ждёт, api и Postgres из интернета
недоступны вовсе.

## Наблюдение

Grafana на `http://127.0.0.1:3000` (вход — из `env/grafana.env`), Prometheus на
`http://127.0.0.1:9090`. Дашборд «Чеки» заведён провижинингом и лежит в
репозитории: [deploy/grafana/dashboards/receipts.json](deploy/grafana/dashboards/receipts.json).

Grafana выведена наружу — `https://root-hub.ru:41142` из интернета и
`https://192.168.100.114:41142` из локальной сети, см. раздел
[«Публикация Grafana»](#публикация-grafana). Prometheus наружу не выведен вовсе:
смотреть его с самой машины или через SSH-туннель.

```bash
ssh -N -L 9090:127.0.0.1:9090 user@192.168.100.114
```

**Ручных шагов нет.** Grafana читает содержимое чеков из Postgres отдельной
ролью только на чтение, и роль заводит одноразовый сервис `grafana-db-init` —
он ждёт, пока api накатит миграции, выдаёт гранты и выходит; Grafana стартует
только после его успешного завершения. Скрипт идемпотентен и прогоняется на
каждом `docker compose up -d`, поэтому смена пароля в env-файле доезжает до базы
сама. Он же запускается руками, если нужно:

```bash
docker compose exec db sh /opt/sql/10-grafana-readonly.sh
```

Почему именно так, а не миграцией и не хуком базы:

- **хук `initdb` не подходит** — он выполняется при создании кластера, когда
  таблиц ещё нет (их создаёт alembic из контейнера api), а `GRANT` на
  несуществующую таблицу роняет инициализацию базы целиком;
- **миграция не подходит** — её применяет точка входа api под `set -euo
  pipefail`, и ей понадобился бы `GRAFANA_DB_PASSWORD`: не задан — api не
  стартует, то есть вся система падает из-за ненастроенной Grafana. Сверх того,
  роль и пароль — не состояние схемы: пароль меняют, права досыпают, а миграция
  выполняется однажды, «переприменить» её нечем, и `downgrade` не смог бы просто
  удалить роль — `DROP ROLE` отказывает, пока за ролью числятся права.

Пароль берётся из `GRAFANA_DB_PASSWORD` в `env/postgres.env` и должен совпадать
с одноимённой переменной в `env/grafana.env`.

**Что откуда берётся.** Разделение жёсткое и намеренное:

| Что смотрим | Источник | Почему так |
|---|---|---|
| Сколько сканов, отказы по причинам, задержка внешней расшифровки | Prometheus | Числа во времени. Метрики есть только у `checks_service`: он один видит скан целиком |
| Точное число чеков и позиций, содержимое QR, шапка чека, товары | Postgres (`grafana_ro`) | Содержимое в метрику не положить: строка чека в метке означала бы отдельный временной ряд на каждую покупку |

Содержимое чека показано на двух разных стадиях, и путать их не надо:

- **«Позиции чека — как их отдал фискальный сервис»** читает `checks.raw_payload`
  и видна **сразу после сканирования**. Это чек как он есть у налоговой:
  название, количество, цена, а у сербского ещё ГТИН и ставка НДС;
- **«Позиции, записанные в реестр»** читает `records` и наполняется только
  **после разбора чека в боте** — там к товару уже добавлены тип и категория.

Пока чек стоит в очереди `/check`, первая таблица по нему полна, вторая пуста.

Счётчики Prometheus живут в памяти процесса и обнуляются при перезапуске
`checks-service`; SQL-панели считают по строкам и потому точны. Расхождение
между двумя панелями «Отсканировано чеков» — свойство, а не сбой, и на дашборде
об этом написано.

Роль `grafana_ro` видит ровно четыре таблицы (`users`, `spreadsheets`, `checks`,
`records`) и только на `SELECT`: [deploy/postgres/grafana_readonly.sql](deploy/postgres/grafana_readonly.sql).
Новая таблица не станет видимой Grafana сама собой — её добавляют туда руками.

За входом в Grafana видно, кто что покупал: QR-строка целиком, ссылка на чек на
сайте налоговой, каждая позиция с ценой. Пустой `GF_SECURITY_ADMIN_PASSWORD`
оставляет `admin/admin` — пароль обязателен.

## Публикация Mini App

Единственная публичная часть системы — Mini App: Telegram открывает его только
по HTTPS. Конфиг — [deploy/nginx/mini_app.conf.example](deploy/nginx/mini_app.conf.example),
один файл.

Раскладка: `accounting.root-hub.ru` ведёт на шлюз `95.31.139.53`, он же
терминирует TLS и проксирует HTTP на `192.168.100.114`, где живут nginx и весь
стек. Отсюда два адреса у одной страницы — `https://accounting.root-hub.ru/`
снаружи и `http://192.168.100.114/` из локальной сети: имя изнутри уходит на
шлюз и без NAT loopback обратно не возвращается. Оба имени обслуживает один
server-блок.

```bash
sudo cp deploy/nginx/mini_app.conf.example /etc/nginx/sites-available/mini_app.conf
sudo ln -s /etc/nginx/sites-available/mini_app.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

1. В скопированном файле проверить `root` — путь до `mini_app/` внутри клона.
2. Если репозиторий лежит в домашнем каталоге, выдать nginx проход: команды
   `setfacl` в шапке конфига. Иначе статика отвечает 403 при живом `/api`.
3. BotFather → Bot Settings → Menu Button → URL `https://accounting.root-hub.ru/`.
4. Открыть меню бота **с телефона**: штатный сканер QR есть только в мобильном
   Telegram. Телефон должен быть в мобильной сети, а не в домашнем Wi-Fi, —
   иначе он упрётся в тот же NAT loopback.

```bash
curl -s -H "Host: accounting.root-hub.ru" http://127.0.0.1/   # статика, с самой машины
curl -s  https://accounting.root-hub.ru/                      # она же снаружи
curl -si -X POST https://accounting.root-hub.ru/api/v1/mini-app/checks/preview
# 401 от сервиса — цепочка шлюз → nginx → checks-service собрана целиком
# (подписи initData в curl нет и быть не может).
# «Welcome to nginx» снаружи при рабочем локальном ответе — шлюз не передаёт Host.
# 404 — запрос не дошёл до сервиса: чаще всего из-за слэша в конце proxy_pass.
# 403 — nginx не может прочитать файлы, см. пункт 2.
```

Статика и `/api` обязаны отдаваться **с одного имени**: страница ходит в бэкенд
по относительному пути, а `CORSMiddleware` в `checks_service` нет намеренно.

Миграции применяет `scripts/entrypoint.sh` при старте контейнера api.

`google_sheets_service` работает без входящих запросов, поэтому его `/health`
отдаёт не «жив ли процесс», а итог последнего прохода: сколько задач взято,
сделано и провалено. Ручной проход — `curl -X POST localhost:8011/sync`.

## Публикация Grafana

Вторая — и последняя — публичная точка системы. Конфиг:
[deploy/nginx/grafana.conf.example](deploy/nginx/grafana.conf.example).

Раскладка похожа на Mini App, но **TLS терминируется на хосте**, а не на шлюзе.
Причина в способе публикации: Proxmox пробрасывает 41142 порт-в-порт (DNAT), то
есть шифрованное соединение идёт насквозь от браузера до `192.168.100.114`, и
снять TLS по дороге некому. Nginx хоста расшифровывает и отдаёт запрос
контейнеру на `127.0.0.1:3000`; сам контейнер наружу не публикуется.

Отсюда два адреса у одного входа, оба по HTTPS: `https://root-hub.ru:41142`
снаружи и `https://192.168.100.114:41142` из локальной сети (имя изнутри сети
уходит на шлюз и без NAT loopback не возвращается). Оба перечислены в SAN
сертификата, поэтому работают оба.

Сертификат самоподписанный: публичный CA не выдаёт сертификаты на приватные
адреса, а настоящий сертификат `root-hub.ru` живёт на шлюзе и обслуживает его
443-й порт. Цена — одно предупреждение браузера на каждом новом устройстве:
«Дополнительно» → «Перейти». `Strict-Transport-Security` по этой же причине
**не включён**: с самоподписанным сертификатом он убирает из Chrome кнопку
«перейти всё равно» и закрывает вход наглухо.

```bash
# 1. Сертификат на 10 лет — на имя И на оба адреса
sudo mkdir -p /etc/ssl/grafana
sudo openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
  -subj "/CN=root-hub.ru" \
  -addext "subjectAltName=DNS:root-hub.ru,IP:192.168.100.114,IP:95.31.139.53" \
  -keyout /etc/ssl/grafana/grafana.key -out /etc/ssl/grafana/grafana.crt
sudo chmod 600 /etc/ssl/grafana/grafana.key

# 2. Конфиг
sudo cp deploy/nginx/grafana.conf.example /etc/nginx/sites-available/grafana.conf
sudo ln -s /etc/nginx/sites-available/grafana.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 3. Firewall — если он включён
sudo ufw status                    # inactive — не включать, ничего не делать
sudo ufw allow 41142/tcp           # только если active
```

4. На Proxmox — проброс **TCP** 41142 → `192.168.100.114:41142`. Именно проброс,
   а не HTTP-прокси: TLS снимается на хосте, и попытка разобрать поток как HTTP
   упрётся в первый же байт рукопожатия.
5. Длинный случайный пароль в `env/grafana.env`, затем
   `docker compose up -d grafana`. Пароль переприменяется из файла при каждом
   старте контейнера, смена его в интерфейсе живёт до ближайшего перезапуска.

```bash
ss -ltnp | grep -E '41142|3000'   # 41142 — nginx; 3000 — по-прежнему 127.0.0.1
curl -k -sI https://127.0.0.1:41142/login              # 200, с самой машины
curl -k -s  https://192.168.100.114:41142/api/health   # "database": "ok"
curl -k -sI https://root-hub.ru:41142/login            # снаружи, из другой сети
# Connection refused снаружи при рабочем локальном ответе — нет проброса на Proxmox.
# Соединение рвётся на рукопожатии — Proxmox разбирает 41142 как HTTP вместо TCP.
# Вход зацикливается на форме логина — до Grafana не доходит X-Forwarded-Proto.
# Панели не обновляются сами — не проксируется /api/live/ (WebSocket).
```

**Что теперь видно за этим входом.** Форму логина видит кто угодно в
интернете: ограничений по адресу источника нет — это сознательное решение.
Проверки подписи initData, как у Mini App, здесь нет и быть не может, поэтому
единственная защита — пароль. Против подбора на nginx стоит `limit_req` на
`/login`: 10 попыток в минуту с адреса, дашбордов ограничение не касается. За
паролем — QR-строка каждого чека, ссылка на него на сайте налоговой и каждая
покупка с ценой.

Prometheus (`127.0.0.1:9090`) и `/metrics` сервисов наружу **не выводятся**: в
метриках `checks_service` лежит `telegram_id` — кто и когда сканировал чеки.

## Разработка

```bash
uv sync
uv run ruff check .
uv run mypy api checks_service google_sheets_service telegram_bot tests
```

Тестам нужен настоящий Postgres 16 (схема использует нативные enum,
`GENERATED ... AS IDENTITY` и `UNIQUE NULLS NOT DISTINCT`, поэтому SQLite не
подходит):

```bash
docker run -d --name pg-test -e POSTGRES_PASSWORD=test -p 5544:5432 postgres:16
uv run pytest
```
