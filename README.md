# Cost accounting — новая версия

Учёт личных расходов. Postgres — источник истины, Google Spreadsheet — отчётная
поверхность и интерфейс редактирования справочников.

Система состоит из четырёх частей:

| Часть | Состояние | Ответственность |
|---|---|---|
| `api/` | готов | Владеет Postgres. Вся предметная логика и все деньги |
| `google_sheets_service/` | готов | Единственный, кто ходит в Google API. Разгребает очередь перерисовки листов, читает правки пользователя и отдаёт их в api |
| `telegram_bot/` | **этот шаг** | aiogram-фронтенд: разбирает ввод, зовёт api, печатает ответ по-русски. Здесь же живёт разбор чека |
| `checks_service/` + `mini_app/` | готов | Единственная публичная часть системы: Mini App сканирует QR-код чека, сервис получает расшифровку и кладёт сырьё в api |

## Что сделано на этом шаге

**Разбор чека** — последняя недостающая часть. Сырьё, которое накапливает Mini
App, превращается в операции реестра: `/check` в боте показывает позиции чека,
предлагает тип каждому товару, раскладывает типы по категориям и спрашивает
счёт. Записывается всё одним запросом и одной транзакцией.

Типы знакомых товаров берутся из кэша `cashed_records` без обращения к модели;
модель зовётся дважды и только за неизвестным — типы для незнакомых товаров и
категории для новых типов. Её ответ проверяется схемой, а не разбирается
«на глазок»: именно на этом ветка чеков в старой версии разваливалась целиком.

Прежде чем что-либо записать, разбор сверяет сумму позиций с итогом чека —
целочисленно, в копейках. Расхождение означает, что прочитано не то поле, и чек
не записывается вовсе.

Подробности: [docs/BOT_machine.md](docs/BOT_machine.md) §10 и
[docs/CHECKS_machine.md](docs/CHECKS_machine.md) §8.

## Ключевые архитектурные решения

**Api никогда не ходит в Google.** Изменение данных — одна короткая транзакция в
Postgres, которая заодно пишет строку в очередь `sheet_sync_tasks`. Отдельный
сервис разгребает очередь и перерисовывает листы, повторяя при сбоях. Поэтому
операция не может завершиться сообщением об ошибке после того, как деньги уже
списаны, — сценарий двойного списания при таймауте на стороне Google исчезает.

**Задача в очереди описывает не изменение, а устаревание.** Строка означает
«лист X таблицы Y больше не соответствует БД». Уникальный ключ
`(spreadsheet_id, target, period_id)` схлопывает десять быстрых правок в одну
задачу, а перерисовка идёт из текущего состояния БД целиком — поэтому повтор
безопасен, а порядок обработки не важен.

**Баланс счёта — производная величина.** Колонки `current_balance` нет: баланс
считается агрегатом от начального баланса, операций и переводов. Расхождение
баланса с реестром становится невыразимым.

**Период — строка в таблице, а не подвижный указатель.** `periods` с уникальным
`(spreadsheet_id, start_date)` делает ролловер идемпотентным и позволяет догнать
любое число пропущенных месяцев. Границы полуинтервальные: `[start, end)`.

**Деньги — `NUMERIC(14,2)` и `Decimal`.** Ни одного `float`, ни одного
округления по пути от БД к листу.

**Принадлежность чужой таблице невыразима.** Составные внешние ключи
`(category_id, spreadsheet_id) → categories(id, spreadsheet_id)` не дают
сослаться на категорию из чужого документа — раньше это проверялось вручную в
каждом сервисе и местами было забыто.

## Запуск

```bash
cp env/api.env.example env/api.env
cp env/postgres.env.example env/postgres.env
cp env/google_sheets_service.env.example env/google_sheets_service.env
cp env/telegram_bot.env.example env/telegram_bot.env
cp env/checks_service.env.example env/checks_service.env
# заполнить пароли, положить ключ сервисного аккаунта в secrets/google_sa.json,
# указать TELEGRAM_BOT_TOKEN, ALLOWED_TELEGRAM_IDS и PROVERKACHEKA_API_TOKEN
docker compose up -d --build
curl -s localhost:8010/health          # api
curl -s localhost:8011/health          # отчёт последнего прохода по очереди
curl -s localhost:8012/health          # бэкенд Mini App
```

Ни один порт наружу не публикуется: всё висит на `127.0.0.1`. Бот работает
через long polling и входящих соединений не ждёт, api и Postgres из интернета
недоступны вовсе.

## Публикация Mini App

Единственная публичная часть системы — Mini App: Telegram открывает его только
по HTTPS. Конфиг — [deploy/nginx/mini_app.conf.example](deploy/nginx/mini_app.conf.example),
один файл.

Раскладка: `accounting.root-hub.ru` ведёт на шлюз `95.31.139.53`, он же
терминирует TLS и проксирует HTTP на `192.168.100.114`, где живут nginx и весь
стек. Отсюда два адреса у одной страницы — `https://accounting.root-hub.ru/`
снаружи и `http://192.168.100.114/` из локальной сети: имя изнутри уходит на
шлюз и без NAT loopback обратно не возвращается. Оба имени обслуживает один
server-блок.

```bash
sudo cp deploy/nginx/mini_app.conf.example /etc/nginx/sites-available/mini_app.conf
sudo ln -s /etc/nginx/sites-available/mini_app.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

1. В скопированном файле проверить `root` — путь до `mini_app/` внутри клона.
2. Если репозиторий лежит в домашнем каталоге, выдать nginx проход: команды
   `setfacl` в шапке конфига. Иначе статика отвечает 403 при живом `/api`.
3. BotFather → Bot Settings → Menu Button → URL `https://accounting.root-hub.ru/`.
4. Открыть меню бота **с телефона**: штатный сканер QR есть только в мобильном
   Telegram. Телефон должен быть в мобильной сети, а не в домашнем Wi-Fi, —
   иначе он упрётся в тот же NAT loopback.

```bash
curl -s -H "Host: accounting.root-hub.ru" http://127.0.0.1/   # статика, с самой машины
curl -s  https://accounting.root-hub.ru/                      # она же снаружи
curl -si -X POST https://accounting.root-hub.ru/api/v1/mini-app/checks/preview
# 401 от сервиса — цепочка шлюз → nginx → checks-service собрана целиком
# (подписи initData в curl нет и быть не может).
# «Welcome to nginx» снаружи при рабочем локальном ответе — шлюз не передаёт Host.
# 404 — запрос не дошёл до сервиса: чаще всего из-за слэша в конце proxy_pass.
# 403 — nginx не может прочитать файлы, см. пункт 2.
```

Статика и `/api` обязаны отдаваться **с одного имени**: страница ходит в бэкенд
по относительному пути, а `CORSMiddleware` в `checks_service` нет намеренно.

Миграции применяет `scripts/entrypoint.sh` при старте контейнера api.

`google_sheets_service` работает без входящих запросов, поэтому его `/health`
отдаёт не «жив ли процесс», а итог последнего прохода: сколько задач взято,
сделано и провалено. Ручной проход — `curl -X POST localhost:8011/sync`.

## Разработка

```bash
uv sync
uv run ruff check .
uv run mypy api checks_service google_sheets_service telegram_bot tests
```

Тестам нужен настоящий Postgres 16 (схема использует нативные enum,
`GENERATED ... AS IDENTITY` и `UNIQUE NULLS NOT DISTINCT`, поэтому SQLite не
подходит):

```bash
docker run -d --name pg-test -e POSTGRES_PASSWORD=test -p 5544:5432 postgres:16
uv run pytest
```
