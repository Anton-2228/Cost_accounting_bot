# `telegram_bot` — карта модуля

Документ для последующих сессий. Описывает, **что сделано** в
`new_version/telegram_bot`, какие инварианты нельзя нарушать и что делать
дальше. Парные документы — [API_machine.md](API_machine.md) и
[GSHEETS_machine.md](GSHEETS_machine.md).

Пиши на русском: сообщения пользователю, комментарии, докстринги, сообщения
коммитов.

---

## 1. Что это

Третья и последняя часть системы. Бот не владеет ничем: разбирает ввод, зовёт
api и печатает ответ по-русски. Ни драйвера БД, ни ключей Google здесь нет.

**Одна внешняя зависимость всё же появилась** — ключ OpenAI. Она пришла вместе с
разбором чека (§10): типы товаров и категории для новых типов подсказывает
модель, и другого способа их получить у бота нет. Прежняя формулировка «никаких
внешних ключей» с этого шага неверна, и обходить это молчанием было бы хуже
самого факта. Границы зависимости узкие: весь `openai` заперт в
`telegram_bot/ai/`, ключ нужен только команде `/check`, и ни одна другая команда
без него не меняется.

Интерфейс текстовый, как в старой версии: `/add 500 еда карта обед`.
Экранная навигация эталонного `sales_analysis` (пейджеры, дерево
callback-фабрик) **не переносилась** — она не нужна при вводе одной строкой.

Проверено, а не заявлено:

| Проверка | Команда | Результат |
|---|---|---|
| Линтер | `uv run ruff check .` | чисто |
| Типы | `uv run mypy api checks_service google_sheets_service telegram_bot tests` | чисто, 397 файлов |
| Тесты | `uv run pytest` | 586 |

## 2. Поверхность команд

```
/start           мастер: название → день сброса → часовой пояс → почта
/help            справка (двумя сообщениями: в одно не помещается)
/cancel          прервать любой диалог

/add       <сумма> <категория> <счёт> [пометка...]
/del       [id]                       без id — последняя операция периода
/add_trans <сумма> <откуда> <куда>    [пометка...]
/del_trans [id]                       без id — последний перевод периода

/check           разобрать чек из очереди: типы → категории → счёт
/check_skip      отложить текущий чек (только внутри разбора)
/check_del       удалить текущий чек (только внутри разбора)

/table           ссылка на документ
/table_sync      вчитать правки справочников из листов (ответ — уведомлением
                 на каждый лист: подтверждение либо разбор ошибки)
/table_email     открыть доступ ещё одной почте
/table_delete    отвязать таблицу (после слова «ПОДТВЕРЖДАЮ УДАЛЕНИЕ»)
```

`/check_skip` и `/check_del` зарегистрированы **внутри** состояний разбора и
только там: вне разбора нечего откладывать и нечего удалять. В меню Telegram они
при этом есть — в меню попадает только зарегистрированное, и обратное правило
(«объявить в меню то, чего как команды не существует») было ошибкой старой
версии, а не это.

Ключ команды в `Manager` совпадает с командой Telegram без слеша, поэтому
второй таблицы соответствий не существует.

Из возможностей api, которых не было в старой версии, добавлено **только
удаление перевода**: раньше ошибочный перевод гасили встречным, и в реестре
навсегда оставались две лишние строки.

## 3. Конвенции

Те же, что в `API_machine.md` §3: один класс — один файл, `from __future__ import
annotations` после докстринга модуля, русские докстринги на модуль, класс и
каждый публичный метод, приватные атрибуты `self._x`, логирование %-стилем,
строка до 100 символов.

Дополнительно:

- **Помощники сгруппированы в классы**, а не оставлены функциями модуля:
  `AmountParser`, `RecordParser`, `AssociationMatcher`, `MoneyFormatter`,
  `ApiErrorPresenter`. Без состояния — `@staticmethod`/`@classmethod`.
- **Разбор возвращает pydantic-модель**, а не пару «значение или строка».
  Ошибка — исключение `ParseError` с готовым русским текстом. В старой версии
  сосуществовали два протокола: `ParseResult` в одном месте и словарь
  `{"status": "success"|"error"}` в другом.
- **Тексты — в `.txt`**, читаются с явным `encoding="utf-8"`.

## 4. Инварианты, которые нельзя нарушать

1. **`Manager.launch` ловит всё.** Не только `ApiError`. Любое исключение →
   сообщение пользователю + `logger.exception`. В старой версии `ValueError`,
   `KeyError` и `TypeError` уходили мимо обработчика, и пользователь не получал
   ничего — по логам это выглядело как успешная команда.
2. **`message.text` проверяется на `None`** на каждом шаге диалога. Фотография
   или стикер вместо ответа давали `TypeError` и запирали пользователя в
   состоянии.
3. **Второго хранилища состояния нет.** Всё промежуточное — в FSM-данных в
   Redis. Словарь `self.temp_data[user_id]` на экземпляре команды не
   воспроизводится ни при каких обстоятельствах: он не чистился при
   `state.clear()`, тёк на весь срок процесса и расходился с FSM после
   перезапуска.
4. **`/cancel` — настоящая команда для всех состояний**, всегда чистит FSM.
   Отсюда свойство: ловушек нет, выход есть всегда и он один.
5. **Ошибка не ставит состояние.** Неудачный `/table_sync` печатает текст и
   ничего не переключает. Старый `CORRECT_TABLE` съедал все команды кроме
   самого `/sync`, включая удаление таблицы.
6. **Неверное подтверждение снимает состояние.** Иначе следующее сообщение
   пользователя снова трактуется как подтверждение — ровно это делал старый
   `DeleteTable`.
7. **Везде `from_user.id`, нигде `chat.id`** для поиска документа. В группе это
   разные числа, и старая версия из-за расхождения искала таблицу по id чата в
   одной команде и по id пользователя во всех остальных.
8. **FSM-данные читаются через `.get()`**, не подпиской.
9. **Сумма уходит в api без знака.** Знак — свойство категории. Минус во вводе
   не принимается вовсе (`AmountParser` отвергает `<= 0`).
10. **Деньги — `Decimal` до самого текста сообщения.** Ни одного `float`.
11. **Справочники не кэшируются.** Единственный источник истины по ним — api;
    любой кэш дал бы окно, в котором только что добавленная категория «ещё не
    существует».
12. **Подбор по псевдониму возвращает первое совпадение.** Дублей не бывает:
    `(spreadsheet_id, alias)` уникален, пространства имён категорий и счетов
    раздельные.
13. **Ответ модели валидируется схемой** (`ai/models.py`), а не обходится
    словарём. Ровно на этом разваливалась ветка чеков: `for x, id in answer:`
    давал `ValueError` мимо обработчика, в тишину.
14. **Позиции чека сверяются с его итогом.** Σ позиций против `totalSum`, в
    копейках, целочисленно. Расхождение — отказ: чек не записывается. Это
    единственная проверка того, что разбор читает те поля, которые думает.
15. **Правка типа не теряется.** В `commit` уходит итоговый тип по **каждой**
    позиции, включая взятые из кэша, — `CashedRecordRepository.upsert`
    переучивает сам. В старой версии правка у уже распознанного товара не
    записывалась никуда.
16. **`callback_data` несёт `check_id`, обработчик фильтруется по состоянию.**
    Без первого кнопка предыдущего чека применилась бы к текущему; без второго
    она осталась бы живой после выхода из разбора.
17. **Пропущенный чек ничего не сохраняет.** `processed_at` у него остаётся
    пустым, а список пропущенных живёт в FSM-данных ровно затем, чтобы очередь
    не зациклилась на нём в пределах одной сессии.

## 5. Уведомления: push и дочитка

У фоновой работы (`google_sheets_service`, ролловер) нет способа ответить
пользователю синхронно, а текст разбора листа рождается тогда, когда
HTTP-запроса пользователя уже нет.

**Основной путь — push.** `NotificationLoop` в `lifespan` api раз в
`NOTIFICATION_PUSH_INTERVAL_SECONDS` берёт недоставленные и толкает боту:

```
POST /notify {notification_id, telegram_id, kind, text}
```

Договор описан кодом ответа бота:

- **204** — «дальше не повторять»: отправлено либо отправить невозможно в
  принципе. Api ставит `delivered_at`. Неисправимые отказы перечислены в
  `_PERMANENT_ERRORS`: `TelegramForbiddenError` (бот заблокирован),
  `TelegramNotFound` и `TelegramBadRequest` (в том числе «chat not found» —
  пользователь ни разу не писал боту, а начать диалог первым бот не может).
- **503** — временная неудача (`TelegramRetryAfter`, сетевой сбой, 5xx).
  Сообщение остаётся в очереди и уйдёт следующим проходом.

Граница существенна в обе стороны. Отвечать 204 на всё подряд нельзя: тогда
`delivered_at` означал бы «api попробовал», а не «пользователь увидел». Но и
503 на неисправимый отказ нельзя: сообщение зависает в очереди навсегда, каждые
15 секунд роняя в журнал один и тот же стектрейс, а вместе с ним встают и все
последующие уведомления этого пользователя.

Сетевая ошибка обрывает **весь проход**: бот недоступен для всех сообщений
сразу, и продолжать значило бы сложить полсотни таймаутов подряд.

**Страховка — дочитка.** `NotificationCatchUp` вызывается из
`BaseCommand.spreadsheet()` — это единственная точка, где бот одновременно знает
документ и разговаривает с его владельцем. Подтверждение общее с push
(`POST .../notifications/{id}/delivered`), поэтому одно сообщение не уйдёт
дважды. Ошибки дочитки глушатся: она сопровождает команду пользователя и не
имеет права её уронить.

Адресация — причина, по которой push вообще понадобился: уведомление знает
только `spreadsheet_id`, а отправлять надо в чат. `telegram_id` лежит через две
таблицы, и без него бот не смог бы узнать, у кого спрашивать, не заведя
собственный список пользователей — второй источник истины о том, кто есть.

## 6. Что изменилось в api ради этого шага

Миграции не потребовалось.

- `UserNotificationRepository.list_undelivered_all(limit)` — вся очередь одним
  запросом с join'ом до `users.telegram_id`.
- Доменная модель `PendingNotification` (`api/domain/pending_notification.py`) —
  результат выборки с join'ом, обратного отображения в ORM нет.
- `NotificationService.list_pending()`.
- `api/tasks/notification_loop.py` + запуск в `lifespan`.
- Настройки `bot_notify_url`, `notification_push_interval_seconds`,
  `notification_push_timeout_seconds`. **Пустой `BOT_NOTIFY_URL` выключает
  рассылку**: api обязан подниматься и без бота — в тестах и до его
  развёртывания.

Существующие эндпоинты чтения и подтверждения уведомлений сохранены: по ним
работает дочитка.

**Виды уведомлений** (`NotificationKind` в `api_client/models.py` — зеркало
`api/enums/notification_kind.py`): `TABLE_READY`, `IMPORT_OK`, `IMPORT_ERROR`,
`SYNC_FAILED`, `ROLLOVER`. Текст бот не сочиняет ни для одного — печатает
`notification.text` как есть, потому что все они собраны из данных документа.
`IMPORT_OK` появился вместе с листом чеков (`e5a1f83b2c47`): раньше `/table_sync`
отвечал «задачу поставили» и на успехе замолкал навсегда. Зеркало перечисления
обязано пополняться вместе с api — `kind` разбирается строгим `StrEnum`, и
незнакомое значение уронило бы разбор **всего** списка уведомлений, а не одного.

## 7. Ошибки api → русский текст

Всё в `errors.py`, одним местом.

| Код | Чем различается | Пример |
|---|---|---|
| 404 | `details.resource` | `category` → «Такой категории нет, либо она выключена» |
| 409 | `details.reason` | `spreadsheet_not_ready` → «Таблица ещё создаётся — пришлю ссылку» |
| 422 | **печатается `message` как есть** | «Период с 2026-07-01 закрыт» |
| 5xx, сеть | — | «Сервис данных недоступен, попробуйте позже» |

422 — сознательное отступление от правила «русский текст живёт в боте»: текст
собран из данных документа и номеров, кодом его не выразить. Ровно та же
причина, по которой русскими приходят разбор листа и уведомления.

`product_type_taken` — единственный 409, чей текст собирается, а не берётся из
таблицы по коду: назвать чужую категорию необходимо, иначе отказ выглядит
беспричинным — пользователь не знает, куда «молочка» уже отнесена, и повторяет
ту же правку. Оба слова в тексте приезжают из `details` как данные.

`spreadsheet_not_ready` встречается чаще всего сразу после `/start`: строки в
базе есть, документа ещё нет, и почти любая команда упирается в проверку
готовности. Для пользователя это ожидание, а не отказ, — текст обещает ссылку.

## 8. Развёртывание

- `dockerfiles/telegram_bot.Dockerfile`, запуск `python -m telegram_bot.main`.
- В `docker-compose.yml` два новых сервиса: `redis` (с `appendonly`, чтобы
  диалог пережил перезапуск) и `telegram-bot`. Порт notify-сервера наружу **не
  публикуется**: его зовёт только api из docker-сети, а сам бот работает через
  long polling и входящих соединений не ждёт.
- Сервису `api` добавлен `BOT_NOTIFY_URL: http://telegram-bot:8002/notify`.
- `env/telegram_bot.env` + `.example`.
- **`TELEGRAM_PROXY_URL`** — прокси только для сессии Bot API
  (`AiohttpSession(proxy=...)` в `telegram_bot/init.py`). Пусто — напрямую.
  Заворачивать сюда остальной трафик нельзя: к api учёта бот ходит по
  внутренней сети Compose (`http://api:8000`), и внешний прокси такой адрес не
  разрешит; провайдер модели задаётся своим `OPENAI_BASE_URL`.
  Схема `socks5://` работает только при установленном `aiohttp-socks` — он в
  зависимостях проекта.
- **`ALLOWED_TELEGRAM_IDS` пустой означает «никому»**. Это не перестраховка:
  `/start` заводит документ в Google на общий сервисный аккаунт с квотой 60
  запросов в минуту на весь проект, и открытый бот позволил бы исчерпать её
  чужими руками.

## 9. Грабли

1. **`NoDecode` для `ALLOWED_TELEGRAM_IDS`.** pydantic-settings пробует
   разобрать значение сложного типа как JSON **до** валидатора, и `1,2` валит
   процесс на старте ошибкой разбора JSON. Аннотация
   `Annotated[frozenset[int], NoDecode]` отключает это и отдаёт строку
   валидатору.
2. **Токен проверяется на формате конструктора `Bot`.** Заглушка вроде
   `test:token` не проходит: для локальных проверок нужен токен вида
   `123456:AAH...`.
3. **Порядок регистрации обработчиков существенный.** aiogram отдаёт сообщение
   первому подошедшему. Поэтому: `/cancel` — раньше всех и во всех состояниях;
   затем «любая другая команда посреди диалога» → подсказка; и только потом
   шаги диалогов. Без второго правила `/table`, набранный внутри мастера, ушёл
   бы в разбор шага и получил «Странный ввод», как в старой версии.
4. **Меню Telegram содержит только зарегистрированное.** Старая версия
   объявляла `/cancel`, `/skip` и `/remove`, которых как команд не
   существовало: они сравнивались строкой внутри разбора чека и вне тех
   состояний отвечали «Не понимаю о чем речь», а форма `/cancel@ИмяБота` не
   срабатывала никогда.
5. **`Decimal.as_tuple().exponent` типизирован как `int | Literal["n","N","F"]`.**
   Буквенные значения бывают только у `NaN` и бесконечности — их надо отсеять
   раньше, иначе mypy справедливо ругается на унарный минус.
6. **Разделитель разрядов — обычный пробел.** Узкие и неразрывные пробелы
   разные клиенты Telegram рисуют по-разному, а в журнале их не найти поиском.
7. **Состояние диалога переживает перезапуск.** Оно в Redis, а не в памяти
   процесса. Неразобранные чеки лежат в api (таблица `checks`), тоже переживая
   перезапуск, — при добавлении разбора эти два хранилища не надо путать.
8. **`chat not found` — это `TelegramBadRequest`, а не `TelegramNotFound`.**
   Ловилось поначалу только `TelegramForbiddenError`, и уведомление на
   `telegram_id`, который никогда не писал боту, повторялось каждые 15 секунд
   бесконечно. Отсюда правило: терминальность определяет **класс ответа
   Telegram**, а не число попыток, — тот же принцип, что у
   `google_sheets_service` с кодами Google (`GSHEETS_machine.md` §2.11).
   Начать диалог первым бот не может: пока пользователь не отправил `/start`,
   отправить ему нельзя ничего.
9. **Пустой `TELEGRAM_PROXY_URL` — это «без прокси», а не пустой адрес.**
   Валидатор `_empty_to_none` в `telegram_bot/config.py` приводит пустую строку
   к `None`; иначе `AiohttpSession` получил бы `""` и упал бы на разборе схемы
   при старте. Отсюда же правило «нет прокси — нет и своей сессии»: `Bot`
   получает `session=None` и заводит умолчательную.

## 10. Разбор чека: как сделано

**Вход бота не касается.** Чеки попадают в БД через Telegram Mini App:
`checks_service` + `mini_app`, см. [CHECKS_machine.md](CHECKS_machine.md). Mini
App запускается через Menu Button в BotFather, а не командой.

**Диалог живёт в боте.** Из двух вариантов («в боте» и «в Mini App») выбран
первый: здесь уже есть FSM, подбор по псевдонимам и русские тексты, а в Mini App
их пришлось бы завести заново — вместе со вторым местом, где они могут разойтись
с ботом.

### Поток одного чека

```
/check ──► GET /checks?unprocessed=true ──► старейший, не попавший в пропущенные
   │
   ├─ raw_payload ──► ReceiptExtractor ──► позиции (Decimal, рубли) + шапка
   │                        └─ Σ позиций ≠ totalSum, operationType ≠ 1 → отказ
   │
   ├─ CHECK_TYPES:      кэш cashed_records → модель (только незнакомые товары)
   │                    правки «1,3 - молочка», кнопка «Готово»
   ├─ CHECK_CATEGORIES: category_product_types → модель (только новые типы)
   │                    правки теми же строками, подбор AssociationMatcher
   └─ CHECK_SOURCE:     один счёт на чек ──► POST /checks/commit ──► следующий чек
```

Три стадии, а не одна: правка типа меняет то, о чём спрашивать дальше.

### Принятые решения

| Решение | Выбор |
|---|---|
| Признак разбора | `checks.processed_at` + `records.check_id` (составной FK) |
| Роль модели | Два вызова: типы для незнакомых товаров, категории для новых типов |
| Дата операций | День разбора, период текущий — `commit_check` этого не меняет |
| Гранулярность | Позиция = операция |
| Нулевые позиции | Пишутся как есть; `CHECK amount <> 0` снят с `records` |
| Канарейка | Σ позиций против `totalSum`; расхождение — отказ |
| Возвраты (`operationType ≠ 1`) | Отказ с внятным текстом и предложением `/check_del` |
| Формат правок | Строки «1,3 - молочка» + кнопка «Готово» |
| Пропуск | Ничего не сохраняет: чек вернётся следующей сессией |
| Удаление | Без подтверждения, мягкое (сырьё остаётся, ключ освобождается); разобранный чек — 409, его убирают удалением операций |
| Нераспознанное | «НеопределенныеТраты», `product_type = NULL` |
| Тип занят другой категорией | 409 с названием чужой категории, чек не записывается |
| Отказ модели | Сообщение, FSM чистится, чек остаётся неразобранным |

### Что из старой реализации не повторяется

- `AddCheck.py:227` — `for x, id in answer:` по словарю: `ValueError` на первом
  же чеке с незакэшированным товаром, мимо обработчика ошибок, в тишину. Ветка
  чеков была нерабочей целиком. Теперь ответ модели валидируется схемой
  (`ai/models.py`), а её форма плоская: список пар «номер → значение».
- Правки пользователя молча терялись: тип, исправленный у товара с уже
  распознанным типом, никуда не записывался. Теперь в `commit` уходит итоговый
  тип по **каждой** позиции, а `CashedRecordRepository.upsert` переучивает кэш.
- `requests.post` без таймаута в асинхронном коде. Внешних вызовов у бота теперь
  два — api и модель, — и у обоих таймаут задан явно.
- Callback-обработчики без фильтра по состоянию: кнопка от предыдущего чека
  оставалась живой. Теперь `callback_data` несёт `check_id`, а регистрация
  ограничена состояниями разбора.
- `self.temp_data[user_id]` на экземпляре команды. Черновик разбора
  (`checks/draft.py`) целиком лежит в FSM-данных и переживает перезапуск вместе
  с ними.
- Промпт «достать реквизиты из текста чека» не перенесён: реквизиты разбирает
  `checks_service/formats/ru_fns/parser.py` из QR-строки. Первый из двух вызовов
  модели исчез вместе со старым форматом входа, а с ним — целый класс ошибок.

### Что изменилось в api ради этого шага

Миграция `d4c7b2e910a3`, подробности — в [API_machine.md](API_machine.md) §9.

- `checks.processed_at` + партиальный индекс очереди и `UNIQUE (id,
  spreadsheet_id)` как цель составного FK;
- `records.check_id` вместо `records.check_json`: копия расшифровки лежала в
  каждой позиции чека, хотя сам чек уже хранится строкой в `checks`;
- снят `CHECK amount <> 0`;
- `?unprocessed=`, `DELETE .../checks/{id}`, `check_id` в `CommitCheckRequest`.
